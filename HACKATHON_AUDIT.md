# Velora hackathon release audit

**Audited:** 27 October 2026 · **Requested repository:** [Amit-yadav12/Velora_Hack](https://github.com/Amit-yadav12/Velora_Hack) · **Live demo:** [velora-ai-in.netlify.app](https://velora-ai-in.netlify.app/)

## Executive verdict

**43/100 — promising prototype, not ready to claim trustworthy real bookings or a production-ready release.** Discovery, India-specific presentation, and the breadth of the prototype are useful, but a failing build, tenant authorization exposure, booking races, and QR/check-in defects are decisive blockers. The score is a judgment against the requested rubric, not a prediction of a competition result.

I reviewed the requested repository's `main` at [`83c2c074ae3d31d45e57dddc21b6b5c26f510bdb`](https://github.com/Amit-yadav12/Velora_Hack/commit/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb) using a separate source snapshot. The code fixes in this session exist only in the attached `Velora_12` working tree; **none have been applied to `Velora_Hack` or deployed**. No live database, Storage bucket, deployment, production records or GitHub branch was changed. No PR was opened. To implement these remedies in the requested repository, start a session attached to `Velora_Hack`, then port and independently verify the relevant changes.

## Highest-severity findings in the requested source

1. **Critical — business owners receive platform-wide admin power.** [`api/register-business.js`](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/api/register-business.js#L34-L45) grants `role: 'admin'` before inserting the business. [`api/admin.js`](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/api/admin.js#L17-L44) then lets any admin list all bookings and customer profiles and mutate resources without an ownership filter. A local mocked-Supabase probe reproduced: failed business insertion → account remains admin → overview exposes two other mock tenants' bookings. No live account or customer data was accessed.
2. **Critical — booking is not atomic or reliably persisted.** [`api/book.js`](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/api/book.js#L176-L227) performs a separate overlap read and insert, supplemented by an in-memory ledger that is not shared across serverless instances. In a local mocked concurrency probe, two simultaneous same-staff/same-time requests both received 201 and distinct saved mock rows after both read an empty conflict set. No live database race was run. With a missing database, a separate local probe returned 201 with `status: confirmed`, `demo_mode: true`, and `pipeline.saved: false`. A client-supplied Google-place snapshot is also treated as booking inventory, and the registered-business service lookup is not scoped to its business.
3. **Critical — QR validation/check-in does not establish a real current appointment.** [`verify-booking.js`](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/api/verify-booking.js#L34-L66) returns `valid: true, demo: true` when no row is found or the database is unavailable. The [QR helper](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/api/_lib/qr.js#L9-L16) uses a publicly known development secret if none is configured. A no-row token verified in a local unconfigured probe. A separate mocked row probe showed a rescheduled booking's old signed time still validates. The target's [`api/bookings.js`](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/api/bookings.js) permits an admin status change to `checked_in` without verifying a ticket; the UI uses that status action. The target's Netlify `Permissions-Policy` also sets `camera=()`, which would block a browser scanner if one were added. Live secret configuration and exploitation were **not** tested.
4. **Critical — public database policy exposure depends on deployment grants.** Target [0001](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/supabase/migrations/0001_velora_core.sql#L278-L303) permits all-profile reads and anonymous booking inserts in RLS; 0003 does not replace those policies. If the deployment retains the usual Supabase client table grants, these policies allow unintended direct access. Effective live grants and RLS were not inspected.
5. **High — bootstrap can remove unrelated policies.** Target [0001](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/supabase/migrations/0001_velora_core.sql#L269-L275) drops **every** RLS policy in the `public` schema, not only Velora-owned policies. Do not execute it or its unguarded generated bundle on an existing/shared database. Back up and review an incremental migration path first.
6. **High — scanned/pasted ticket URLs truncate.** [`tokenFromInput`](https://github.com/Amit-yadav12/Velora_Hack/blob/83c2c074ae3d31d45e57dddc21b6b5c26f510bdb/src/services/verify.ts#L19-L26) accidentally excludes the literal lowercase `s`. On the target source, `https://example.test/verify/v1.sample.signature?source=qr` returned only `v1.`. This is fixed only in the attached branch.
7. **High — onboarding and location/media are incomplete.** The target has a two-step signup with optional starter service; production business editing is described in its UI as database-managed. There is no demonstrated owner upload/persistence flow or pin confirmation. If signup requires email confirmation, the current form returns before registering the submitted business, and no completed post-confirmation registration was verified. Service insertion errors are logged while the endpoint can still report success.

## Work completed in the attached branch

The attached branch already contained substantial earlier work: scoped authorization, additive migration 0005, transaction-based bookings, signed QR verification, real-media onboarding, maps and honest demo/provider separation. This audit added three further fixes there:

- Corrected scanned/pasted QR URL token extraction. Five new regressions cover lowercase `s`, query/fragment/whitespace, an actual demo link and a mocked verification request.
- Fixed camera lifecycle races: streams arriving after dialog close/unmount are stopped; old detector results cannot submit; immediately granted streams attach after the preview mounts. Four jsdom regressions use mocked camera and API calls.
- Guarded generated `supabase/APPLY_ALL.sql` so it refuses existing public RLS policies or relations before application DDL. Historical 0001 remains unchanged and dangerous if run directly. The isolated SQL suite verifies refusal and a fresh bootstrap; this does not replace a real backup or staging review. Added a high/critical dependency-audit step to this branch's CI workflow; no remote run has tested it.

After a clean `npm ci`, the attached branch passed lint, build, `sql:check`, and `npm audit` with **0 advisories**. Its verification suite passed **111 demo, 4 demo-auth, 119 integration, 30 isolated SQL, 60 mocked API/input, 4 mocked camera and 147 jsdom app checks**. These numbers do not describe the requested target repository or prove live integrations. See [FINAL_REPORT.md](FINAL_REPORT.md) and [DEPLOY.md](DEPLOY.md) for this branch's files and safe rollout caveats.

## Five highest-impact next steps

1. **Attach the correct repository and remove tenant exposure first.** Separate business owner from explicit platform operator, scope every service-role query by stable business ID, tighten RLS/grants, and test two owners, a customer, anonymous access and a trusted operator. Never apply a destructive bootstrap to production.
2. **Make real reservations and check-in authoritative.** Use transactional database locking/exclusion and customer-scoped idempotency; validate service/staff ownership and hours; fail closed on database/signing failure; require a persisted, current signed ticket and authorized check-in. Run true parallel multi-session tests.
3. **Finish onboarding and real inventory.** Implement recoverable email-confirmed signup, editable business details, verified owned uploads, location confirmation, INR services and saved hours. Test reload, failed upload/save and cross-tenant edits against staging Supabase/Storage.
4. **Repair the actual demo and release pipeline.** Fix the `fit_score` type mismatch, date-dependent/Node-version tests, vulnerable lockfile and legacy bootstrap risk; produce a passing CI run. Deploy a known commit to staging, then verify the live card/detail/API agree and label all synthetic content and illustrations.
5. **Prove the experience with real evidence.** Exercise real Auth, Maps, email/Calendar/reminders and physical camera on desktop/mobile with failure states; add distributed abuse protection, monitoring, retry/alerting, accessibility testing and interviews with real providers/customers. Report only services actually verified.

## Honest judge demo sequence

1. **Problem and boundaries (30 seconds):** describe the local-service booking problem and clearly announce whether this is a synthetic offline sample or connected staging. Never describe synthetic businesses, reviews or slots as real.
2. **Discovery (45 seconds):** select Jaipur and a category, show search and explain the ranking and INR service prices. On the current live site, avoid relying on the inconsistent MI Road detail until it is corrected.
3. **Owner setup (60 seconds):** on the attached local sample, show the multi-step form and its honest no-backend refusal. Only demonstrate publish/upload on a verified staging project with the owner's own real test images and address.
4. **Customer booking and ticket (60 seconds):** in connected staging, book a genuinely available slot, show the committed appointment and signed QR. If staging is unavailable, show a clearly labelled local sample request and explain that it does not reserve a real business.
5. **Trust and failure (45 seconds):** in verified staging, demonstrate an altered or cancelled ticket, an unauthorized owner, and a competing slot request; show failure rather than a fabricated success. Describe email/Calendar as unverified unless provider logs and a test inbox confirm them.
6. **Close (30 seconds):** summarize current limitations, next milestones and the user problem. A credible demo does not guarantee a winning score.
