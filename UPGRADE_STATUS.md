# Upgrade assessment (28 Oct 2026)

## Scope and status
The existing React/Vite application, serverless API and Supabase migrations remain in place. Routes include `/welcome`, `/reset-password`, `/explore`, `/business/:id`, `/appointments`, `/notifications`, `/profile`, `/settings`, `/onboard`, `/admin/*`, and `/verify/:token`. Public discovery is intentionally browseable without sign-in; booking APIs require authentication.

This is **not a production-readiness certification**. The requested shared, isolated demo backend was not implemented. Sample identities and records are stored in the browser and only work on the same browser profile; they cannot support simultaneous users on different devices. The demo is available only when browser Supabase configuration is absent, not alongside a configured live project. Web Locks serialize demo booking attempts across tabs where supported; browsers without Web Locks do not have that cross-tab guarantee. Do not use the local demo as an actual booking system. Local QR tokens are not server-signed and only verify against that browser's records.

The existing live API uses signed QR tokens and a database reservation RPC, and migrations define authorization policies. These mechanisms have automated mocked/PGlite coverage, but a real configured Supabase project, real concurrent clients, provider delivery, and deployed camera scanning have not been verified here. No migrations were applied or changed during this work. Phone-only sessions can reserve and retrieve bookings by authenticated user ID without an email; this path has mocked API coverage but still needs testing against a configured SMS provider and real Supabase project. Business registration still requires an account email. Per-process API rate limiting is best-effort and does not provide distributed abuse protection on serverless deployments. Notification history, realtime and reminder delivery require deployed database configuration and a separately configured scheduler; the existence of a reminder endpoint alone does not schedule it.

Incomplete browser Supabase configuration now displays an error rather than silently switching to demo. The live booking review displays the server invoice price rather than adding the sample-only GST calculation.

The local demo booking write now fails explicitly when browser storage is unavailable and no longer truncates booking history to 100 records. Terminal demo tickets are rejected for verification. Notification read failures are surfaced. Auxiliary demo invoice and notification writes are still best-effort and are not transactional with bookings. Real monetary representation and complete production readiness require further review; do not treat demo invoice tax as a tax determination.

## Configuration and verification
See `.env.example` and `DEPLOY.md` for environment and deployment setup. Live deployment needs matching browser Supabase URL and anon key, server Supabase URL and service-role key, a stable `QR_SIGNING_SECRET`, and deployed origin configuration. Phone OTP requires a Supabase SMS provider and rate-limit configuration; maps, email, calendar and scheduled reminders need their respective optional configuration. Never put service credentials in `VITE_*` variables. Google sign-in is disabled in the interface.

Build/type-check, lint, SQL bundle checks and existing automated verification were run locally. The Playwright suite could not launch: the available Chromium binary lacks required system libraries in this environment; install it in an environment with access to the Playwright browser download host and run `npm run verify:browser`. Browser, real provider and deployed end-to-end scenarios must not be considered verified based on the mocked or DOM-based tests.
